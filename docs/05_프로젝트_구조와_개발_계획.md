## 2. 제품 기본 기획

**목표:** 고등학생이 오늘 할 일을 실행 가능한 단위로 나누고, 집중·휴식·회고를 반복하도록 돕는다.

대표 흐름은 ‘오늘 60분 공부하기 → 수학·영어 할 일 입력 → 계획 검토 → 집중 시작 → 휴식 → 결과 기록 → 다음 행동 제안’이다. 시작 부담과 중단 후 재시작을 우선 해결한다.

핵심 원칙은 계정 없는 시작, 학생이 승인하는 계획 변경, 기기 내 기록, 짧은 입력이다. 공부 시간 경쟁이나 연속 기록에 대한 벌점은 두지 않는다. 웹 앱이 다른 앱 사용을 자동 감시하거나 스마트폰을 강제 차단한다고 표현하지 않는다.

첫 구현은 모바일에서도 사용할 수 있는 반응형 웹으로 한다. 실제 AI 연결 전에는 규칙 기반 제안을 제공하고 그 출처를 표시한다. AI 제공자와 서버 운영 방식은 아직 확정하지 않는다.

## 3. 핵심 기능과 우선순위

| 우선순위 | 기능 | 최초 제공 범위 | 완료 기준 |
| --- | --- | --- | --- |
| P0 | 오늘의 학습 계획 | 과목·할 일·가용 시간 입력, 순서·시간 수정, 확정 | 집중·휴식·회고 합계가 가용 시간을 넘으면 초과 표시 및 수정 가능 |
| P0 | 집중·휴식 타이머 | 기본 25분/5분, 길이 변경, 시작·일시정지·재개·중단 | 일시정지·휴식 제외, 복원 시 중복 집계 방지 |
| P0 | 기록과 회고 | 완료·일부 완료·미완료, 선택적 난이도·중단 사유 | 확정 기록 저장, 새로고침 후 복원, 결과 중복 저장 방지 |
| P0 | 데이터 설정 | 전체 삭제, AI 전송 기본 꺼짐, 기기 저장 안내 | 원본·파생 기록 삭제, 저장 실패를 화면에 표시 |
| P1 | 통계 | 일별·주별·과목별 시간과 계획 완료율 | 원본 기록과 일치, 계획 없는 날은 ‘계획 없음’ |
| P1 | 기본 코칭 | 기록 요약과 한 가지 제안, 수락·수정·거절 | 거절 시 계획 유지, 수락 시 한 번만 변경 |

| P2 | 선택적 알림 | 별도 동의, 빈도·조용한 시간 적용 | 기본 꺼짐, 알림 권한 거절 시 앱 사용 가능 |

기본 MVP는 P0와 P1을 포함한다. 외부 AI와 알림은 이를 검증한 뒤 확장한다. 계정·서버 동기화, 보호자 화면, 친구 순위, 문제 풀이, 결제는 초기 범위에서 제외한다.

## 4. 화면과 사용자 흐름

| 화면 | 주요 요소 | 이동 |
| --- | --- | --- |
| 오늘 `/` | 오늘 할 일, 진행 상황, 다음 세션, 시작 버튼 | 계획 또는 집중 |
| 계획 `/plan` | 할 일 입력, 가용 시간, 계획 초안·수정·확정 | 집중 |
| 집중 `/focus` | 선택한 할 일, 남은 시간, 제어 버튼, 휴식·회고 | 회고 후 오늘 |
| 기록 `/history` | 날짜별 세션, 주간·과목별 요약, 빈 상태 안내 | 오늘 |
| 코치 `/coach` | 근거 요약, 제안 한 가지, 수락·수정·거절 | 승인한 계획 |
| 설정 `/settings` | 시간 기본값, 배지·알림·개인화·AI 동의, 전체 삭제 | 이전 화면 |

회고는 집중 화면의 하위 단계로 두어 화면 이동 부담을 줄인다. 첫 방문은 계정 가입 없이 오늘 할 일 하나를 입력하고 시작할 수 있게 한다. 모바일은 하단 탐색, 넓은 화면은 사이드 탐색을 고려한다. 키보드 조작, 명확한 포커스, 색 외 상태 표시를 제공하고 타이머 초 단위 변화를 계속 음성으로 읽지 않는다.

## 6. 기술 구성과 데이터 설계

React + TypeScript + Vite를 사용한다. 초기 UI 상태는 React 기본 상태 관리로 시작하고, 도메인 계산은 UI와 분리된 순수 함수로 작성한다. 추가 라이브러리는 구현 단계에서 필요한 범위만 선정하고 버전·호환성을 확인한다.

| 모델 | 주요 필드·역할 |
| --- | --- |
| StudyTask | id, subject, title, estimatedMinutes, priority, completion |
| DailyPlan | id, localDate, timeZone, availableMinutes, revision, items, confirmedAt |
| PlanItem | id, taskId, kind(focus/break/reflection), plannedMinutes, order |
| FocusSession | id, planItemId, subjectSnapshot, status, 실행 구간, 종료 시각, 확인 상태 |
| Reflection | sessionId, completion, optional difficulty/interruptionReason |
| CoachSuggestion | id, basis, proposedChanges, basePlanRevision, response |
| BadgeAward | badgeKey, periodKey, earnedAt |
| UserSettings | 집중·휴식 기본값, 시간대, AI·개인화·알림·배지 설정 |

데이터는 버전 정보를 포함한 기기 내 저장소로 시작한다. 초기 규모에서는 localStorage 어댑터를 사용하되 React 렌더링과 분리한다. 접근 불가·용량 초과·손상 시 조용히 덮어쓰지 않고 저장되지 않았음을 알려야 한다. 규모가 커지면 어댑터 뒤를 IndexedDB로 바꿀 수 있다. 기기 간 동기화는 없다.

학습 시간은 확정한 실행 구간의 합계다. 계획 시간과 실제 실행 시간을 분리한다. 계획은 수정 버전을 보관해 조언 생성 이후 변경된 계획을 오래된 제안으로 덮어쓰지 않게 한다. 상세 기록 기본 90일과 관련 파생 데이터 삭제는 기존 기획 기준을 따른다. 브라우저 데이터 삭제나 기기 변경으로 기록을 잃을 수 있음을 안내한다.

## 7. 타이머와 AI의 핵심 설계

타이머는 `idle → running ↔ paused → completed/interrupted`로 동작하며 휴식은 별도 종류의 세션으로 구분한다. setInterval 호출 횟수로 시간을 세지 않고 저장한 실행 구간의 시각 차로 계산한다. 화면 갱신 주기와 시간 계산을 분리한다.

새로고침·절전·브라우저 복귀 시 실행 상태와 종료 기준을 재계산한다. 비정상 종료 이후 실제 공부 여부가 불확실하면 사용자 확인을 받은 후 확정하며 예정 시간을 넘겨 자동 기록하지 않는다. 여러 탭에서 동시에 실행·저장하지 않도록 활성 세션 소유권과 저장 이벤트를 확인한다. 자정 경과 시 설정 시간대별로 실행 구간을 나눠 집계한다. 웹 백그라운드에서 종료 알림이 반드시 울린다고 보장하지 않는다.

코칭은 공통 인터페이스 뒤에서 규칙 기반 제공자와 외부 AI 제공자를 교체한다. AI 응답은 허용된 필드·시간 범위를 검증한 제안으로만 취급하고 계획 적용은 별도 함수가 담당한다. AI 키를 Vite 클라이언트 환경 변수에 넣지 않는다. 실제 연결 시 비밀 키를 보관하는 서버 엔드포인트를 별도로 설계한다. 삭제·동의 철회 이후 진행 중 요청의 응답은 버린다.

## 8. 단계별 개발 계획

기간은 일정 약속이 아닌 소규모 개발 작업량 초안이며 담당 인력과 사용자 검증 결과에 따라 조정한다.

| 단계 | 작업 | 산출물·통과 기준 | 예상 작업일 |
| --- | --- | --- | --- |
| 1. 기반 | 기존 산출물 보존, Vite React TS 초기화, 스타일·화면 뼈대 | 개발 서버·프로덕션 빌드·타입 검사 성공, 6개 화면 이동 | 1~2일 |
| 2. 계획·저장 | 타입·저장 어댑터, 할 일 편집, 시간 검증, 계획 확정 | 새로고침 복원, 초과 계획 안내, 빈 상태·저장 실패 처리 | 2~3일 |
| 3. 집중·회고 | 상태 전환, 실행 구간, 복원·중복 방지, 결과 기록 | 계획 → 타이머 → 회고의 전체 흐름, 복원 시 기록 검증 | 3~4일 |
| 4. 기본 MVP | 일·주 통계, 규칙 코칭, 배지, 삭제·보관 정책 | 집계 정확성, 제안 승인, 파생 데이터 삭제 검증 | 3~4일 |
| 5. AI 확장 | 제공자 선정, 서버 경계, 동의, 출력 검증·대체 안내 | 미동의·오류 시 기본 기능 유지, 승인 없는 변경 없음 | 2~4일 |
| 6. 사용성 검증 | 모바일·키보드·빈 상태·오류 흐름 확인, 시범 피드백 | 주요 결함 수정, 사용자 불편과 후속 우선순위 기록 | 2~3일 |

첫 개발 단위는 단계 1~3의 연결된 기본 흐름이다. 외부 AI 선정과 시범 사용자 모집 일정은 위 개발 작업일에 포함하지 않는다. 알림은 기본 MVP 안정화 후 필요성과 브라우저 지원을 확인해 추가한다.

## 9. 검증 계획

- 단위 검증: 계획 시간 합계, 일시정지 제외, 자정 분할, 완료율 분모, 배지 중복 방지, 보관 기간 삭제.
- 통합 검증: 새로고침 복원, 여러 탭 동시 조작, 손상·접근 불가 저장소, AI 제안 시 계획 버전 충돌, 삭제 후 늦은 AI 응답.
- 사용자 흐름 검증: 신규 입력 → 계획 수정·확정 → 집중·휴식 → 회고 → 통계 확인 → 전체 삭제.
- AI 확장 검증: 미동의, 응답 지연, 잘못된 형식, 과도한 시간 제안, 거절·수락 중복 요청.
- 화면 검증: 좁은 모바일 화면, 키보드만 사용, 긴 할 일, 기록 없음, 저장 실패 안내.

구현 단계마다 타입 검사와 프로덕션 빌드를 확인한다. 테스트 도구는 구현 착수 시 선정한다. 현재는 문서만 작성했으므로 앱 실행·테스트를 완료한 상태가 아니다.

`focusmate-web/`의 기존 dist를 보존한 뒤 React + TypeScript + Vite 소스를 초기화하고, 오늘·계획·집중 화면을 연결한다. 첫 구현 목표는 AI 연결 없이 할 일 하나를 계획하고 집중 세션을 마친 뒤 결과가 저장되는 흐름이다.

사용자 선택에 따라 웹 우선으로 구현한다. 집중 타이머 실행 중 화면이 5초 이상 숨겨졌다가 돌아오면 복귀 안내를 한 번 표시한다. 타이머는 유지하며 계속하기·쉬기·종료를 선택하게 한다. 특정 앱 감지·차단이나 이탈을 실패로 판정하는 기능은 포함하지 않는다. P0 타이머 범위로 단계 3에서 구현하며, 설정·중복 표시 방지·종료 우선 처리 등은 [집중 복귀 안내 설계](06_집중_복귀_안내_설계.md)를 따른다.
